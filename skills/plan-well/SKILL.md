# /plan-well

계획 문서를 쓴다. 산출물은 **본문 1개 + 시각 문서 1개 + 결정 기록 1개**다.

```
/plan-well                      # 현재 작업을 계획 문서로
/plan-well <주제>               # 주제로 새 계획
/plan-well --update <파일>      # 기존 계획 갱신 (본문은 제자리 재작성, 결정은 누적)
```

## 산출물

| 파일 | 내용 | 갱신 방식 |
|---|---|---|
| `[<기능>] plan.md` | 목표 · 범위 · 단계 · 검증 · 용어 · 유효 결정 · 열린 질문 | 제자리 재작성 |
| `[<기능>] flow.html` | 전체 흐름 + 범위 · 검증 · 용어. 본문에서 링크 | 본문과 같이 재작성 |
| `[<기능>] decision.md` | 결정마다 문제 · 옵션 · 근거 + 출처 · 영향도 태그 | **누적**. 지우지 않음 |

저장 위치 · 파일 이름 · 링크 규칙은 **[`docs-writing`](../docs-writing/SKILL.md) 스킬을 따른다** — 시작 전에 읽는다.

```
docs/
  2026-09-10-new-feature/
    [new-feature] plan.md
    [new-feature] flow.html
    [new-feature] decision.md
```

파일 이름에 공백 · 대괄호가 있다. markdown 링크는 `<...>` 로 감싸고, 셸에서는 따옴표로 감싼다.

본문에 다이어그램을 인라인하지 않는다. 계획이 길어지고 흐름만 보려는 사람이 못 찾는다.

## 필수 섹션

아래 3개는 **본문과 HTML 양쪽에 반드시** 있다. "빈 섹션은 지운다" 규칙의 예외.

| 섹션 | 쓰는 것 | 금지 |
|---|---|---|
| 범위 | `한다` / `안 한다` 목록. 경계가 애매한 항목은 `안 한다` 에 명시 | "등", "기타" 로 끝내기 |
| 검증 | 무엇을 · 어떻게(명령 · 테스트 · 수동 절차) · 통과 기준. 단계 완료 기준과 연결 | "동작 확인", "테스트한다" 같은 판정 불가 문장 |
| 용어 | 이 계획에서 쓰는 고유 용어 · 약어 · 의미가 좁혀진 일반어. `용어 — 정의 (코드/경로)` | 사전적 정의 복붙. 정말 없으면 `없음` 한 줄 |

HTML 에서는 접기 · 클릭 상세 안에 넣지 않는다. 펼친 상태로 보이게 한다.

## 3원칙

### 1. 간결

- 필요한 것만. 배경 설명·의의·기대효과 문단 금지.
- 한 항목 = 한 줄. 두 줄 넘으면 하위 항목으로 쪼갠다.
- 코드 예시는 규약을 못 정하는 경우에만. 구현을 미리 쓰지 않는다.
- 본문 목표 200줄 이하.

### 2. 처음 보는 사람 기준

- 대화 맥락·이전 결정을 안다고 가정하지 않는다.
- 약어 · 고유명사는 `용어` 섹션에 모은다. 본문 첫 등장에서도 편다.
- 첫 화면(상단 15줄)에 **무엇을 왜 만드는가**와 시각 문서 · 결정 기록 링크가 있어야 한다.

### 3. 본문은 이력 금지, 이력은 decision.md 에만

계획이 바뀌면 본문은 **현재 계획으로 제자리 재작성**한다. 최종 상태만 남는다.

- 본문 금지: `기존엔 A였으나 B로 변경`, `~~취소~~`, `(2차 수정)`, 변경 이력 섹션.
- 왜 바뀌었는지는 `decision.md` 에 결정으로 남기고, 본문은 그 번호만 참조한다.
- 완료 항목은 지우지 말고 체크만 한다(진행 상태는 이력이 아니다).

## 결정 기록 ([<기능>] decision.md)

의사결정 과정을 남기는 문서. **한 번 쓴 결정은 지우지도 고치지도 않는다** — 누적만.

### 번호

- `D-001` 부터 순서대로. 폴더(기능) 안에서 공유하는 번호 — 본문 · HTML · 커밋 · 대화에서 같은 번호로 가리킨다.
- 번호 재사용 · 재정렬 금지. 뒤집힌 결정도 번호를 유지한다.

### 태그 (결정마다 2개 필수)

| 태그 | 값 | 뜻 |
|---|---|---|
| 출처 | `제안 사람\|AI · 선택 사람\|AI` | 누가 안을 냈고 누가 골랐나 |
| 영향도 | `높음` · `중간` · `낮음` | 뒤집히면 설계가 얼마나 바뀌나 |

영향도 기준:
- 높음 — 데이터 모델 · 외부 인터페이스 · 모듈 경계 · 다른 결정 다수가 기대는 결정
- 중간 — 한 모듈 내부 구조 · 흐름이 바뀜
- 낮음 — 구현 세부. 되돌려도 국소 수정

### 상태

| 상태 | 표시 | 언제 |
|---|---|---|
| 유효 | `유효` | 현재 따르는 결정 |
| 재논의 | `재논의` 라벨 | 다시 논의가 필요. 결론 전까지 유효로 보지 않음 |
| 대체됨 | `Superseded by D-00N` | 새 결정이 이것을 뒤집음 |

- **뒤집을 때**: 새 번호로 새 결정을 쓴다(`Supersedes D-00M`). 이전 결정은 본문을 그대로 두고 `Superseded by D-00N` 마커만 단다.
- **재논의**: 결정에 `재논의` 라벨 + 사유 한 줄. 결론이 유지면 라벨 제거 + 재확정 사유 한 줄, 바뀌면 위 "뒤집을 때".
- 기존 결정에 허용되는 수정은 **마커 · 라벨 · 그 사유 한 줄 추가뿐**이다.

### 형식

```markdown
# <기능> 결정 기록

계획: [plan.md](<./[<기능>] plan.md>) · 흐름: [flow.html](<./[<기능>] flow.html>)

## 현황

| 번호 | 결정 | 상태 | 출처 | 영향도 |
|---|---|---|---|---|
| D-001 | 저장소는 S3 | Superseded by D-004 | 제안 AI · 선택 사람 | 높음 |
| D-002 | 캐시 TTL 10분 | 재논의 | 제안 사람 · 선택 사람 | 낮음 |
| D-003 | 업로드는 서명 URL 직접 업로드 | 유효 | 제안 AI · 선택 AI | 중간 |
| D-004 | 저장소는 R2 | 유효 | 제안 사람 · 선택 사람 | 높음 |

## D-001. 저장소는 S3
- 출처: 제안 AI · 선택 사람
- 영향도: 높음
- 상태: Superseded by D-004
- 날짜: 2026-11-19

### 문제
<무엇을 정해야 했나. 제약 조건>

### 옵션
- A. S3 — <장단>
- B. R2 — <장단>

### 근거
<왜 A. 버린 안을 버린 이유>
```

- `현황` 표는 상태가 바뀔 때마다 갱신한다(유일하게 고쳐 쓰는 곳). 유효 결정을 한눈에 찾는 용도.
- 결정 본문은 파일 아래로 계속 붙인다. 최신이 아래.
- 옵션이 하나뿐이면 결정이 아니다 — 기록하지 않는다.

### 무엇을 결정으로 남기나

- 옵션이 2개 이상이었고, 고른 이유가 코드만 봐서는 안 보이는 것.
- 사용자가 고른 것, AI 가 고르고 사용자가 동의한 것 둘 다. 출처 태그로 구분한다.
- 사소한 이름 · 스타일 선택은 남기지 않는다.

## 시각화

시각 문서는 **`/visual-doc` 스킬이 HTML 1장으로 만든다** ([`visual-doc`](../visual-doc/SKILL.md)).
형식 고르기와 HTML 키트가 거기 있다. 계획 스킬은 무엇을 그릴지만 정한다.

HTML 에 반드시 보이는 것:
- 전체 흐름
- **범위** (한다 / 안 한다)
- **검증** (단계별 방법 · 통과 기준)
- **용어** (표)
- 흐름 위 결정 지점에는 결정 번호(`D-00N`)를 단다. 대체됨 결정은 표시하지 않는다.

**본문이 진실이고 그림은 그 형태다.** 그림에만 있는 정보를 만들지 않는다.

## 본문 템플릿

```markdown
# <제목>

<한 문단: 무엇을 만드는가. 왜 필요한가.>

흐름: [flow.html](<./[<기능>] flow.html>) · 결정: [decision.md](<./[<기능>] decision.md>)

## 범위

- 한다: ...
- 안 한다: ...

## 단계

| # | 단계 | 산출물 | 완료 기준 |
|---|---|---|---|
| 1 | ... | ... | ... |

## 검증

| 대상 | 방법 | 통과 기준 |
|---|---|---|
| 단계 1 | `npm test -- foo` | 전부 통과 |
| 단계 2 | 수동: <절차> | <관찰되는 결과> |

## 용어

| 용어 | 정의 | 위치 |
|---|---|---|
| ... | ... | `src/...` |

## 결정

유효 결정만. 상세 · 이력은 [decision.md](<./[<기능>] decision.md>).

- D-003 업로드는 서명 URL 직접 업로드
- D-004 저장소는 R2
- D-002 캐시 TTL 10분 `재논의`

## 열린 질문

- [ ] ...
```

`범위` · `검증` · `용어` 외의 빈 섹션은 지운다. 채울 게 없으면 그 섹션이 필요 없다는 뜻이다.

## 절차

0. `docs-writing` 스킬을 읽고 폴더를 정한다.
1. 목표 · 범위를 먼저 쓴다. 못 쓰면 계획이 아직 없는 것 — 사용자에게 묻는다.
2. 용어를 모은다. 정의가 안 되는 용어가 있으면 `열린 질문` 으로 올린다.
3. 대화 · 작업 중 내려진 결정을 `decision.md` 에 기록한다(출처 · 영향도 태그 포함).
4. `/visual-doc` 으로 흐름 문서를 만든다(범위 · 검증 · 용어 포함). 그리다 막히는 지점이 실제로 안 정해진 지점이다 — `열린 질문` 으로 올린다.
5. 단계 표를 채운다. 각 단계는 **검증 가능한 완료 기준**을 갖고, `검증` 표에 방법이 있다 ("구현한다" 금지).
6. 본문 상단에서 시각 문서 · 결정 기록을 링크한다.
7. 마지막 점검:
   - 처음 보는 사람이 상단 15줄로 무엇을 왜 만드는지 아는가
   - 범위 · 검증 · 용어가 본문과 HTML 양쪽에 있는가
   - 본문에 이력 문장이 남아 있는가
   - 모든 결정에 출처 · 영향도 태그가 있는가. 본문 `결정` 목록과 `decision.md` 현황 표가 맞는가

## 갱신

`--update` 는 본문 · HTML 은 재작성, 결정은 누적이다.

1. 기존 본문 · `decision.md` 를 읽는다.
2. 새로 내려진 결정 · 뒤집힌 결정을 `decision.md` 에 먼저 반영한다(새 번호 + `Superseded by` / `재논의` 라벨).
3. 본문을 **현재 상태로** 고쳐 쓴다. 무엇이 바뀌었는지는 본문에 쓰지 않는다 — 채팅 응답으로 알린다.
4. HTML 도 같이 고친다. 본문과 그림이 어긋난 계획은 틀린 계획이다.
