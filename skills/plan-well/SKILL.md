# /plan-well

계획 문서를 쓴다. 산출물은 **본문 1개 + 시각 문서 1개**다.

```
/plan-well                      # 현재 작업을 계획 문서로
/plan-well <주제>               # 주제로 새 계획
/plan-well --update <파일>      # 기존 계획 갱신 (제자리 재작성)
```

## 산출물

| 파일 | 내용 |
|---|---|
| `PLAN.md` (또는 `docs/<주제>-plan.md`) | 목표 · 범위 · 단계 · 결정 · 열린 질문 |
| `docs/<주제>-flow.html` | 전체 흐름 시각 문서. 본문에서 링크로 건다 |

본문에 다이어그램을 인라인하지 않는다. 계획이 길어지고 흐름만 보려는 사람이 못 찾는다.

## 3원칙

### 1. 간결

- 필요한 것만. 배경 설명·의의·기대효과 문단 금지.
- 한 항목 = 한 줄. 두 줄 넘으면 하위 항목으로 쪼갠다.
- 코드 예시는 규약을 못 정하는 경우에만. 구현을 미리 쓰지 않는다.
- 본문 목표 200줄 이하.

### 2. 처음 보는 사람 기준

- 대화 맥락·이전 결정을 안다고 가정하지 않는다.
- 약어는 첫 등장에서 편다. 프로젝트 고유명사는 어디를 보면 되는지 경로를 준다.
- 첫 화면(상단 15줄)에 **무엇을 왜 만드는가**와 시각 문서 링크가 있어야 한다.

### 3. 이력 금지

계획이 바뀌면 **현재 계획으로 제자리 재작성**한다. 최종 상태만 남는다.

- 금지: `기존엔 A였으나 B로 변경`, `~~취소~~`, `(2차 수정)`, 변경 이력 섹션.
- 예외 — 이력을 남기는 유일한 경우: **되돌아갈 위험이 있는 결정**. 그때만 `## 결정` 에 한 줄. 형식 `선택 — 이유. 버린 안: X (버린 이유)`.
- 완료 항목은 지우지 말고 체크만 한다(진행 상태는 이력이 아니다).

## 시각화

시각 문서는 **`/visual-doc` 스킬이 HTML 1장으로 만든다** (`~/.claude/skills/visual-doc/`).
형식 고르기와 HTML 키트가 거기 있다. 계획 스킬은 무엇을 그릴지만 정한다.

**본문이 진실이고 그림은 그 형태다.** 그림에만 있는 정보를 만들지 않는다.

## 본문 템플릿

```markdown
# <제목>

<한 문단: 무엇을 만드는가. 왜 필요한가.>

흐름: [<주제>-flow.html](./<주제>-flow.html)

## 범위

- 한다: ...
- 안 한다: ...

## 단계

| # | 단계 | 산출물 | 완료 기준 |
|---|---|---|---|
| 1 | ... | ... | ... |

## 결정

- <선택> — <이유>. 버린 안: <X> (<이유>)

## 열린 질문

- [ ] ...
```

빈 섹션은 지운다. 채울 게 없으면 그 섹션이 필요 없다는 뜻이다.

## 절차

1. 목표·범위를 한 문단으로 먼저 쓴다. 못 쓰면 계획이 아직 없는 것 — 사용자에게 묻는다.
2. `/visual-doc` 으로 흐름 문서를 만든다. 그리다 막히는 지점이 실제로 안 정해진 지점이다 — `열린 질문` 으로 올린다.
3. 단계 표를 채운다. 각 단계는 **검증 가능한 완료 기준**을 갖는다 ("구현한다" 금지).
4. 본문 상단에서 시각 문서를 링크한다.
5. 마지막 점검: 처음 보는 사람이 상단 15줄로 무엇을 왜 만드는지 아는가. 이력 문장이 남아 있는가.

## 갱신

`--update` 는 diff 가 아니라 재작성이다.

1. 기존 파일을 읽는다.
2. 바뀐 부분을 **현재 상태로** 고쳐 쓴다. 무엇이 바뀌었는지는 파일에 쓰지 않는다 — 채팅 응답으로 알린다.
3. 다이어그램도 같이 고친다. 본문과 그림이 어긋난 계획은 틀린 계획이다.
